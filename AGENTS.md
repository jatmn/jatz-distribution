# Contributor and agent rules

Jat'z Distribution is an in-development Factorio 2.1 mod. The artwork is finished and tested in game, the freighter and depots are placeable and drivable with free recipes, and freighters deliver items from provider and buffer depots to request depots, and fluids between the liquid depots, driving only on road. Fuel, and balanced recipes, are next.

## Where things are

- `README.md`: project overview and roadmap.
- `assets/quinityn-freighter/README.md`, `assets/depots/README.md` and `assets/roads/README.md`: what each asset folder holds, how to use the sprites in Factorio, and how to edit and re-render the models. Read the relevant one before changing artwork or tools.
- `docs/testing.md`: how to test in Factorio. Record outcomes in `docs/test-results.md`.
- `concepts/`: approved concept art. Preserve it unchanged.

## Mod source

- The repository root is the mod's root: `info.json`, `data.lua`, `data-final-fixes.lua`, `prototypes/`, `locale/`, and the runtime `control.lua` with `scripts/`.
- The prototypes load the sprite helpers and sheets straight from `assets/` (paths in `prototypes/constants.lua`), so art is never copied. `prototypes/depot-definitions.lua` exists because `depot-pictures.lua` loads its data from that name.
- Prefix every prototype name with `jatz-`, and keep player-facing text in `locale/en/`.
- Placed unrotated, every depot has its loading zone to the south (`prototypes/orientation.lua`). Cargo and Fuel depots are shown half a turn from their artwork, with ports turned too, so their opening faces south; liquid depots load opposite their north-facing pipes. The loading zone marking is each depot's `integration_patch`, so it rotates with the depot. It draws on `ground-patch-higher2`: above decoratives such as plants, below rails, belts, items, buildings and vehicles. Some decoratives (medium and big sand rocks) draw on `floor` or `object`, which no ground layer can beat, so `scripts/loading-zone.lua` removes decoratives overlapping the loading zone tile, as Factorio does under buildings. It does this whenever a depot is built by any means or turned, and for existing depots on first load. `tools/test_mod_setup.py` checks the layout with Lua 5.2.
- **Roads and deliveries.** `jatz-road` (`prototypes/roads.lua`) is a floor tile like stone path. `prototypes/off-road.lua`, run from `data-final-fixes.lua` so every mod's tiles are included, gives every other tile the `jatz_off_road` collision layer. The delivering freighter, `jatz-freighter-drone` (`prototypes/freighter-drone.lua`), is a hidden unit whose only collision layer is that one (tiles only), so the engine's pathfinder routes it over road and nothing else; there is no road-network bookkeeping in Lua. Keep its `path_resolution_modifier` at the default: at 1 the engine finds no path for its 0.8-tile box on a one-tile road. `scripts/logistics.lua` registers provider and request depots, and sends freighters from each short request depot's loading zone to the provider holding the item that is nearest **by road** (both loading zones must be road; depots lay their own, see below). Road distance comes from `surface.request_path` with the freighter's own box and mask, asked one provider at a time in straight-line order; the search stops at the first candidate already farther in a straight line than the best road found, since a road is never shorter. A provider with no road route goes on cooldown and no freighter is sent towards it. Each search carries a token, and its owner (the request depot, or the trip of a freighter being rerouted) holds the token of its one current search. A road or depot change, a changed request, a busy pathfinder (`try_again_later`) or a 10 s timeout replaces or drops the token, so stale answers neither set cooldowns nor send freighters, and the search starts afresh: at the next dispatch for a depot, at once or on the next once-a-second check for a freighter. A freighter waiting for a reroute stays stopped (re-planning and command completions skip it), and if the provider found is emptied or removed meanwhile it searches again rather than leaving. `on_configuration_changed` restarts all searches. `tests/lua/logistics.lua` plays these races out against a fake runtime with Lua 5.2 (run by `tools/test_mod_setup.py`), with the freighter slot's sending, returning, losing and handing back; extend it with any change to the search or the freighters. **Buffer depots** (`jatz-buffer-depot`) are requesting depots like request depots (`logistics.requesting`; their own request, freighters, panel, copy and paste, refunds), but candidates for their freighters are providers only, so stock never bounces between buffers, and they send nothing anywhere. Request depots (item and liquid, never buffer depots) take buffer depots as sources too, and `from_buffers` (the panel's "Request from buffer depots" checkbox, like a requester chest's; carried by copy and paste and blueprint tags; `set_from_buffers`/`get_from_buffers` in the remote interface) decides which kind is ranked first (`first` in `candidates`). Set, buffers come first: the search asks about buffers before providers and never asks about a provider once a buffer has a road, so a nearer provider loses to any reachable buffer; providers cover only what no buffer can. Unset (the default), providers come first and buffers are the fallback, by the same rank rule: a buffer is asked about only when no provider holding the item unpromised and not on cooldown has a road route, so it covers only what no provider can (the owner's choice, November 4, 2026: before, an unset depot ignored buffers even with every provider empty). **Priority:** provider and buffer depots have a priority from 1 to 10 (`depot.priority`, 5 until set: `PRIORITY_DEFAULT`; `set_priority`/`get_priority` in the remote interface, which round and clamp; a slider in the panel: buffer depots have it at the top, above their request, provider depots get a panel with only the slider). It orders depots within their kind only: a candidate's `rank` is its kind (the kind asked about first 0, the other `PRIORITY_MAX`) plus `PRIORITY_MAX - priority`, so every depot of the first kind still comes before any of the other, a higher priority before a lower one however near, and nearest by road among equals; the search's rank rule (stop asking once a rank has a road) covers it unchanged. Changing a priority restarts the searches under way on its surface (`restart_searches`). Copy and Paste settings and clones copy it between provider and buffer depots; blueprints keep it as a `jatz_priority` tag when it isn't 5, applied (if a number) to provider and buffer depots built from the ghost. **Liquid depots** (`jatz-liquid-provider-depot`, `-request-`, `-buffer-`; storage tanks of 25,000 with one fluid storage) take the same roles in `logistics.depots` and are marked `depot.fluid` (`logistics.liquid`): a liquid request depot requests a fluid (`set_request` checks `prototypes.fluid` for liquid depots and `prototypes.item` for item depots), has the same panel (fluid chooser filtered with `FluidPrototypeFilter`s only, which have no `is-parameter`: parameter fluids are left out by their `parameters` subgroup; anchored to `pipe_gui`, the window storage tanks open in 2.1, which removed `storage_tank_gui`; a new fluid request starting at 1000), freighters, from-buffers checkbox (with the same fallback to liquid buffers when unset) and priority, and candidates must be the same kind (`provider.fluid == depot.fluid`), so items and fluids never meet; copy and paste between kinds copies nothing. A fluid trip has `trip.fluid = { amount, temperature }` instead of a cargo inventory (`cargo_amount`/`cargo_empty`), carries at most `FLUID_CAPACITY` (500, Transport Drones' default drone fluid capacity), loads with `remove_fluid(1, amount)` (Factorio 2.1 removed `LuaEntity::fluidbox`: use `get_fluid(1)`, `get_fluid_capacity(1)`, `remove_fluid(1, n)`, which returns the fluid with its temperature, and `insert_fluid`), keeps the temperature, and unloads with `insert_fluid`; fluid that doesn't fit goes back to the provider (state `RETURNING`), and fluid that can't go anywhere is lost (it can't be spilled). A tank holding another fluid gets no room (`need` returns it) and the status `other-fluid` (yellow). Storage tanks have no item inventory, so each liquid request and liquid buffer depot gets a **truck chest** (`jatz-truck-chest`, `prototypes/truck-chest.lua`: an invisible, unselectable, indestructible ten-slot container at the depot's centre that collides with nothing, inserters ignore and blueprints skip), made by `logistics.add` (and `add_all` for older saves, or `truck_chest()` on demand). `truck_chest(entity)`/`freighter_chest(entity)` map a depot to where its freighters arrive as items: the depot itself for item depots, its truck chest for liquid ones; every freighter request, removal, chest count and ctrl+click path goes through them, so robots bring freighters into the truck chest and they move into the slot as usual. A liquid depot's blueprint keeps its freighters only as the `jatz_freighters` tag (a storage tank ghost can't carry an insert plan), and `apply_tags` asks robots for them with `match_freighters` when it is built. The truck chest goes with its depot (`on_object_destroyed`); mining a liquid depot hands the freighters in it to the miner; a cloned truck chest is destroyed, the cloned depot making its own. Request depots hold their own freighters: up to 100 freighter items (`FREIGHTER_CAPACITY`; the item still stacks to 10) in a freighter slot, a script inventory of ten stacks per depot (older one-stack slots are resized) shown as one slot in the request panel; requests, removals and blueprint insert plans spread over chest stacks a stack at a time, and taking freighters into the cursor stops at one stack; freighters put in the depot's chest move into it on the next dispatch (unless freighters are the request); freighters a player moves in by ctrl+ or shift+click in the depot's window, or ctrl+click on the depot in the world, move at once (`take_in_freighters`), and those that don't fit go back to the player's inventory. `on_player_main_inventory_changed` and `on_player_cursor_stack_changed` (registered in `control.lua`) work out what the player moved: how many fewer freighters they carry, inventory and cursor together, than before (counted when they open or point at a request depot, and at every change). Placing from the cursor counts, so a freighter dropped onto the ghost of a requested one moves to the slot at once and the chest slot shows the rest of the request again straight away; moving freighters between inventory and cursor counts as nothing. Freighter requests are lowered by editing the proxies' plans in place (`reduce_freighter_requests`), not by cancelling and requesting anew. Factorio's open container window doesn't redraw a chest's requested-item ghosts for script changes (seen in the owner's video: the ghost kept showing 5 for a request of 4 until the window was reopened). Reopening it by script (over two ticks; within one tick does nothing) worked but visibly flashed the window, and the owner chose no flash: the chest ghost updates when the window is next opened, and the panel's freighter line shows the live count instead, a green "+N" while N freighters are requested, capped by how many more the chest holds than when last seen (`depot.chest_seen`), so freighters already in the chest stay. The depot is the open one, or the selected one for ctrl+click in the world. Only freighters, of any quality: other items moved in stay in the chest as in any container. Freighters waiting in the chest for robots to take away stay too, by count (`logistics.leaving`), so more merged into their stack still move. Construction robots can't reach a script inventory, so freighters are requested like modules: `request_freighters` adds a freighter insert plan (one empty chest stack, 0-based index) to an `item-request-proxy` targeting the depot, never more than the slot has room for counting freighters out, in the chest and already requested; robots fill the chest and the freighters then move to the slot. The panel does this when the cursor holds a freighter ghost (remote view, or none in hand); in remote view it never moves items by hand: a click with an empty cursor cancels the freighter requests (`cancel_freighter_requests`, which leaves other requests alone), and a right-click has robots take the slot's freighters away (`remove_freighters`: they move to an empty chest stack with a freighter removal plan, which the chest-to-slot move skips; right-click again: `cancel_freighter_removal`). Beside the slot (whose number is the freighters at home) a short line always shows how many are out on the road ("3 out", `request_gui.freighter_caption`), so home and out read at a glance, followed by a green "+N" while N freighters are requested; the full breakdown (robots bringing or taking freighters, the slot's limit) is the tooltip of the line and the slot. Pipette over the slot (`jatz-pipette`, a custom input linked to the game's pipette control, with hover tracking via `raise_hover_events`) calls `LuaPlayer.pipette` for the freighter, ghost allowed. A depot sends at most one freighter a second (`SEND_SPACING`, enforced per depot, not just by the dispatch cadence), so they leave one after another, while what the depot still needs, less what its freighters are bringing (`committed`: promised loads outbound, cargo inbound), is above zero and a freighter is in the slot. Each trip promises (`planned`) what it will load: the rest of the need, as far as the provider has it unpromised (`available`, counting every outbound trip to that provider) and it can carry (ten stacks), so the next freighter goes to the next provider nearest by road and large requests are gathered from several. Trips only count towards (`committed`) and hold provider stock for (`available`) the item their depot currently requests: changing the request zeroes the outbound trips' promises, and a rerouted trip promises at most what its new provider has unpromised. The freighter item rides with its trip (`trip.truck`) and goes back into the slot whenever the trip ends; it is lost only if the freighter is destroyed. A freighter with nothing to load, or whose reroute finds no provider, drives home empty to park. The slot holds 100 counting freighters out. Mining a request depot (player, robot or platform: `on_*_mined_entity`, registered in `control.lua` and checked through it by `tests/lua/control-events.lua`, routed to `on_depot_mined`) hands all its freighters, in the slot and out, to the miner's buffer; a depot that dies, or is removed by a script raising `script_raised_destroy`, leaves them on the ground where it stood, freighters still in its chest included (`on_depot_destroyed`, before the entity goes); one removed silently leaves its slot and trip freighters there from `on_object_destroyed`. A freighter arriving to load or unload first stands at the loading zone for 1 s (`LOADING_TICKS`): `on_ai_command_completed` gives it a `stop` command with `ticks_to_wait` and marks the trip `loading`, and the loading or unloading happens when that stop completes. Re-planning skips a loading trip (it plans its route afresh once done), `drive` clears the mark, and a removed depot sends a freighter standing there on at once. One coming home empty parks without stopping. At the provider a freighter loads what it promised, as far as the depot (counting its other freighters) still needs and has room for (`get_insertable_count`), only if the request is still for that item; it brings it back, unloads and parks. Cargo travels as real stacks in a script inventory (`transfer_stack`, `insert` of the stack), never as a name and count, so item data (equipment, spoilage, health) survives; keep it that way. Any failed route puts that provider on a 10-second cooldown for that request; a loaded freighter whose way back is lost returns the cargo to the provider, and only spills it (marked for deconstruction) if that fails too. Changes take effect at once rather than waiting on timers. When road is removed or covered (any tile event, including `script_raised_set_tiles`), every freighter on that surface re-plans, and a route that no longer exists fails in the same tick instead of after the engine's ~6 s stuck timeout. When road is laid, or a depot is built, turned or flipped, that surface's cooldowns are cleared. A removed provider stops its outbound freighter while a search from where it stands finds the next provider nearest by road; a removed request depot sends cargo back to the provider, and an empty freighter just leaves. Re-planning replaces a unit's command, so `behavior_result.deleted` completions are ignored. No fuel yet. Clones of depots are registered with their request; cloned freighters are removed. Copy and Paste settings copies the request and asks robots for the freighters the destination lacks to match the source's (slot, out and coming: `match_freighters`). Blueprints, including copy and paste, keep a request depot's request as a `jatz_request` tag and its freighters as an insert plan into the chest (`on_player_setup_blueprint` → `setup_blueprint`; the blueprint may be the event's record or stack, `blueprint_to_setup` or the cursor, any of them nil); setting a blueprint up again replaces those settings (dropping ones the depot no longer has), keeps other tags and other items' insert plans, and puts freighters only in chest stacks those plans don't use; freighter counts for copying and blueprints are `freighter_total` (slot, out, chest not leaving, coming). A depot built from the ghost takes its request from the tags (`apply_tags`, from every build event that carries tags, using them only if well formed) and gets its freighters through the ghost's item request proxy. Freighter requests remember what they are for (`depot.freighter_target`: the total the depot should end up with, set by `request_freighters`, and from the blueprint's `jatz_freighters` tag for a built ghost). Every dispatch, and every time freighters are put in by hand, keeps the requests to it (`trim_freighter_requests`): requests beyond it are cancelled, and a shortfall nothing covers is requested again, because Factorio drops an item request a player fills by hand even when they put in only part of it; the target is forgotten once the depot has it all, or when the player takes freighters out or has robots take them away (no topping up against them). Freighter requests without a target (Factorio's own from a blueprint ghost: a player building over a ghost passes no tags on) adopt the depot's current total (slot, out, chest, coming) as their target, at every dispatch and when the player opens the depot, before they can fill anything by hand; `match_freighters` to a smaller count cancels the excess requests but never takes freighters away, so freighters put in by hand count towards it and a request already met by hand disappears; robots never overfill the slot. `on_configuration_changed` clears requests and ends trips for items whose mod was removed. Saves from the first version of this code carry cargo as a number: `upgrade()` converts them on use, because the mod version did not change. The console command `/jatz-freighters` prints, for the request depot a player has open or points at, everything the freighter requests are worked out from (slot, out, chest, coming, leaving, target, each request proxy's plans; `logistics.describe_freighters`): use it to see what the game actually did when freighter requests misbehave in play. The request panel (`scripts/request-gui.lua`) is a relative GUI on the request depot's own window. Its status is a light, not text: the game's own status indicator sprites (`utility/status_working` green, `status_yellow`, `status_not_working` red, `status_inactive` grey, style `status_image`) beside the request, with the status text as its tooltip. Green: stocked or on its way; yellow: the item is available but something is in the way; red: no provider has the item; grey: nothing requested. Every status in `logistics.status` needs an entry in `request_gui.lights` (`tests/lua/control-events.lua` checks). `control.lua` owns every event registration, since Factorio keeps one handler per event. The remote interface `jatz-distribution` (`set_request`, `get_request`, `get_status`, `add_freighters` (within the slot's limit; no raw inventory is exposed), `freighter_counts`, `request_freighters`, `requested_freighters`, `cancel_freighter_requests`, `remove_freighters`, `cancel_freighter_removal`) is what the check mod uses.
- **Depot road.** Every depot lays `jatz-depot-road` under its loading zone sign when built (`scripts/depot-road.lua`), so road a tile away connects. It is a separate hidden tile (`prototypes/roads.lua`): it looks and drives like road (no off-road layer, `transition_merges_with_tile = "jatz-road"`) but has no item, and mining it gives nothing, so it can't be farmed. Being its own tile is what marks road the depot owns: `storage.depot_roads[unit_number]` records the tile position and exactly what it covered (tile, hidden and double-hidden tile), and when the depot is removed by any means (`on_object_destroyed`) or turned, that ground comes back, but only if the depot's road is still there and no other depot loads from the same tile. Nothing is laid over existing road, on water or on space platforms. A tile a player places over it, or mining it by hand, gives the spot to the player (mining puts back the covered ground, since mining alone would only reveal the hidden tile); the record becomes `false` so it isn't laid again on load. Depot road with no owner (a cloned area) is adopted, with its hidden tile as the ground. Existing depots get theirs on `on_init`/`on_configuration_changed`. `tests/lua/depot-road.lua` covers turning, mining and covering by hand, sharing (records copied exactly, a missing hidden tile included) and upgrades; `tests/lua/control-events.lua` loads the real `control.lua` and fires the game's events (build, turn, flip, removal, tiles placed, mined or set by players, robots and scripts) at its handlers, so a broken route fails; the check mod covers building, removal and connection. Tiles another mod's script sets over a depot's road (`script_raised_set_tiles`) give the spot up too.
- The freighter is drawn at 60% of the artwork's scale (the owner's choice; it was 75% before) (`constants.freighter_scale`, applied in `prototypes/freighter-art.lua` to both the drivable freighter and the delivering one, with the drivable one's measured boxes scaled to match). The artwork's helper keeps its own scale and checksum; change the size here, never there.
- Our crafting-menu and Factoriopedia row sits directly above the vanilla car and tank row. `data-final-fixes.lua` reads that row's group and order after every other mod has loaded and places ours just before it (`prototypes/placement.lua`). Item order within the row: provider, request, buffer, liquid provider, liquid request, liquid buffer, fuel, the freighter, then road.
- `python3 tools/package_mod.py` builds `dist/jatz-distribution_<version>.zip` from an explicit file list. Add new runtime files to it. Release Please owns version bumps; follow `docs/releases.md` and keep player-facing notes under `Version: Unreleased` in `changelog.txt`. Do not edit version records in ordinary feature PRs.
- After changing the mod, run `python3 tools/test_mod.py --factorio <factorio>` (the free headless server is enough). It loads the packaged zip with and without Space Age, and checks crafting, placement, rotation, pipes, driving, and deliveries over road (a U-shaped road that must be followed, an isolated road tile that must get nothing, a depot without road that must send nothing, armor that must keep its equipment and food its spoilage, a full request depot that must fetch nothing, a destroyed freighter that must be replaced, a request changed mid-trip that must not load the old item, a road cut behind a loaded freighter whose cargo must go back, a freighter that must stand 1 s at each loading zone before loading and before unloading, nothing ever spilled, refused invalid requests, cloned requests, and road laid from a ghost on ground but not water, with every freighter checked to stand wholly on road). Extend `tests/factorio/jatz-distribution-check_0.1.0/control.lua` along with new behavior. Its `EXPECTED_PORTS` table is the designed pipe layout, kept separate from the generated data on purpose: update it only for a deliberate port change.

- **Check the Factorio 2.1 API, never assume it.** 2.1 removed and renamed much of 2.0's runtime API (`LuaEntity::fluidbox`, `defines.relative_gui_type.storage_tank_gui`, ...), and an unknown `defines` value or GUI filter only fails in game. Before using a runtime call, define, GUI parameter or prototype field, look it up in the 2.1 `runtime-api.json` / `prototype-api.json` (lua-api.factorio.com/latest) or the game's `data/changelog.txt`. The Lua harnesses' fakes accept anything unless made strict: `tests/lua/control-events.lua` holds 2.1's `defines.relative_gui_type` list and fails on any other name; do the same for other API surfaces a change relies on.

## Artwork rules

- The `.blend` files under each `source/` folder are the masters. Edit them, then re-render. Never hand-edit sprites.
- The builder scripts (`build_master.py`, `build_depots.py`, `build_connector.py`) **overwrite** the `.blend` files. Carry manual edits into the builder, or don't run it.
- In-game icons (`assets/*/icons/`) are made from the game sprites by `tools/make_icons.py`, so they match what players see: depots face south, and the freighter heads south-east. They're 64 px with three custom mipmaps (120 × 64 PNG, `icon_size = 64`), the layout Factorio 2.1 documents. Regenerate them whenever the sprite sheets change; never edit them by hand.
- Render intermediates (`masters/exr`, `masters/layers`, `masters/shadow-silhouettes`, `masters/render-inputs.json`, `frames/`) are generated and git-ignored. Commit only the resulting `sheets/`, previews and hero renders. The one exception is `assets/depots/connectors/frames/`, which the tools read and which stays tracked.
- Paint masks must stay neutral grayscale. Metal, tires, glass, copper, lights and lenses belong in the untinted base layer.
- **Freighter:** keep the eight wheels, three cargo bays, exposed power unit and cab/clamp/cargo paint split. Render all 64 directions from the same camera, pivot and light. Direction 0 is north, turning clockwise.
- **Depots:** keep the fixed camera, ground pivot, `PROJECTION | tile grid compensation` parent, `SOCKET` markers and pipe shape-key drivers. Pipes must visibly reach the tank. After changes, run the geometry and junction inspectors, the renderer and packager, and the depot test fixture.
- The 1×1 depots in `assets/depots/archive/1x1/` are retired. Keep them out of active builds and fixtures, and don't modify them.
- When changing the default palette, update every place it appears (listed in each asset README).

## Testing rules

- Factorio test runners (`tools/test_factorio.py`, `tools/test_depot_art.py`) build their workspaces under `.local/`. Never touch the user's normal Factorio mods, settings or saves. Unit tests that need scratch files use Python's `tempfile`, which cleans up after itself.
- Headless runs, HTML previews and contact sheets don't prove visual quality. Visual changes need a graphical-client check.
- Keep machine paths, Factorio binaries, logs, saves and Python environments out of commits.
- Screenshots go in the pull request, not the repository. Only images used by the README belong in `docs/images/`.

## Continuous integration

CI (`.github/workflows/ci.yml`) is based on yuoki-quinityn's, but routed by repository **area** so a change only runs the checks for what it touched. `tools/ci_changes.py` reads the complete diff and decides; `CI result` is the one stable check to require.

| Area | Paths | Checks (`.github/workflows/area.yml`) |
| --- | --- | --- |
| Freighter | `assets/quinityn-freighter/`, the freighter test mod, `tools/test_factorio.py`, `tools/prepare_test_mod.py` | Lua and Python lint; Blender sources check when models, images or records change |
| Depots | `assets/depots/` (with the 1×1 archive), the depot test mod, `tools/test_depot_art.py`, `tools/test_depot_lua.py` | Lua and Python lint; generated-Lua test; Blender sources check when models, images or records change |
| Mod | The mod source at the repository root, `tools/package_mod.py`, `tools/test_mod.py` and its check mod, plus anything else that isn't documentation | Lua and Python lint |
| Repository | `.github/`, the other `tools/` | Python lint, the `tools/test_*.py` repository tests, actionlint |

- Documentation (`README.md`, `AGENTS.md`, `CONTRIBUTING.md`, `SECURITY.md`, `docs/`, `concepts/`, licence files) runs no area checks.
- Shared lint configuration (`.luacheckrc`, `.stylua.toml`, `.ruff.toml`, `.gitattributes`) re-checks every area in full. Editing `ci.yml`, `area.yml` or the router runs everything.
- **Lua:** Lua 5.2 syntax, Luacheck and StyLua. Pull requests check the area's changed `.lua` files; pushes to `main` check all of them.
- **Python:** syntax and Ruff (syntax errors and Pyflakes). The frozen 1×1 archive tools are exempt from Pyflakes.
- **Blender sources** (`tools/check_blender_sources.py`, no Blender needed): every `.blend` is saved uncompressed by Blender 4.3; each model matches the hashes in its render, packaging and inspection records; freighter sprites match `checksums.json`; the freighter and every depot have an icon in Factorio's 120 × 64 mipmap layout (decoded and checked for blank levels and stray pixels), made from the current sprite sheets; the loading zone marking is a 64 px tile, not blank, and current with its drawing script; and the 1×1 archive matches its manifest. The art jobs then install the pinned numpy, Pillow and OpenEXR, exercise the real EXR sprite extractor with a small fixture (`tools/test_art_dependencies.py`), redraw the icons (`tools/make_icons.py --check`) and the marking (`make_loading_zone.py --check`), and require the committed pixels to match exactly. Re-render, re-package and re-inspect after editing a model, so the records follow it.
- Changes to `requirements.txt` run both artwork checks so dependency updates must reproduce the committed icons and marking.
- The routing job runs `git diff --check` on every change, except binary files.

**Downloads stay small for area checks.** Area jobs check out text only: blobs over 256 KiB and the binary types in `.gitattributes` are never downloaded, and an area's art is fetched only for its Blender sources check. So text files must stay under 256 KiB; mark larger generated files as `binary` in `.gitattributes` (the routing job fails with that advice otherwise). Keep the checkout exclusions in `ci.yml` and `area.yml` equal to the binary patterns in `.gitattributes`; `tools/test_ci_changes.py` checks that they match.

The installable-package job uses a full checkout when mod, repository tooling or artwork changes, builds the ZIP and verifies its contents, version records and checksum. It is included in `CI result`. Release automation and its tests are documented in `docs/releases.md`.

**A green `CI result` only vouches for the PR's own workflow.** `pull_request` runs use the workflows from the PR, so a PR that edits `.github/workflows/`, `tools/ci_changes.py` or the tools they call can change what is checked, or skip it. Review those changes line by line before merging, whatever CI says; only the owner merges.

Before pushing, format Lua with `stylua --config-path .stylua.toml <files>`, and run `luacheck`, `ruff check --config .ruff.toml` and the relevant `tools/test_*.py`. The tool versions are pinned in the workflow files. When an area or check is added or renamed, update `tools/ci_changes.py`, `tools/test_ci_changes.py` and the jobs in `ci.yml` together. The depot packagers generate `depot-definitions.lua` and `depot-pipe-pictures.lua` through `assets/depots/tools/depot_lua.py`, already in StyLua format; `tools/test_depot_lua.py` requires the committed files to match.

## Repository

The owner has authorized public development. Releases still need the owner's go-ahead. Report vulnerabilities privately using `SECURITY.md`; contribution guidance is in `CONTRIBUTING.md`.

Branch rules are kept as two rulesets matching yuoki-quinityn:
- `.github/main-ruleset.json`: no deleting or force-pushing `main`, and changes go through pull requests with all review threads resolved.
- `.github/ci-ruleset.json`: the `CI result` check must pass.

GitHub only enforces rulesets on private repositories with a paid plan, so apply them when the repository goes public (or the plan is upgraded), and again after editing either file. `python3 tools/apply_rulesets.py` needs `gh` signed in with admin rights. It creates a missing ruleset, updates an existing one by name, and keeps only the oldest if two runs created duplicates; a failed lookup changes nothing.

Dependabot proposes weekly updates for pip and GitHub Actions (`.github/dependabot.yml`); review and test updates before merging. Keep GitHub secret scanning, push protection, private vulnerability reporting, and Python/Actions code scanning enabled. Require approval for outside collaborators' workflow runs and keep action references pinned to commit SHAs.

Pullfrog (`.github/workflows/pullfrog.yml`) runs an AI agent only when the owner posts a new issue or PR comment whose first line is `@pullfrog <instruction>`. `tools/pullfrog_command.py` checks that before any credentials are used; run `python3 tools/test_pullfrog_command.py` after changing either file.
