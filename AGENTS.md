# Contributor and agent rules

Jat'z Distribution is an in-development Factorio 2.1 mod. The artwork is finished and tested in game, the depots are placeable, with balanced recipes unlocked by research (the freighter too, as a drivable car, only with the `jatz-freighter-drivable` startup setting, off by default: `prototypes/freighter.lua` then leaves its item without a `place_result` and hides the car, which stays defined so placed ones survive), and freighters deliver items from provider and buffer depots to request depots, and fluids between the liquid depots, driving only on road, burning fuel and filling up at fuel depots by themselves.

## Where things are

- `README.md`: project overview and roadmap.
- `assets/quinityn-freighter/README.md`, `assets/depots/README.md` and `assets/roads/README.md`: what each asset folder holds, how to use the sprites in Factorio, and how to edit and re-render the models. Read the relevant one before changing artwork or tools.
- `docs/testing.md`: how to test in Factorio. Record outcomes in `docs/test-results.md`.
- `concepts/`: approved concept art. Preserve it unchanged.
- `portal/`: the Mod Portal page (summary, description and gallery), synced by each release (`tools/portal_page.py`, `portal/README.md`). Keep its recipes, research and numbers in step with the mod.

## Mod source

- The repository root is the mod's root: `info.json`, `settings.lua`, `data.lua`, `data-final-fixes.lua`, `prototypes/`, `locale/`, and the runtime `control.lua` with `scripts/`.
- The prototypes load the sprite helpers and sheets straight from `assets/` (paths in `prototypes/constants.lua`), so art is never copied. `prototypes/depot-definitions.lua` exists because `depot-pictures.lua` loads its data from that name.
- Prefix every prototype name with `jatz-`, and keep player-facing text in `locale/en/`.
- Placed unrotated, every depot has its loading zone to the south (`prototypes/orientation.lua`). Cargo and Fuel depots are shown half a turn from their artwork, with ports turned too, so their opening faces south; liquid depots load opposite their north-facing pipes. The loading zone marking is each depot's `integration_patch`, so it rotates with the depot. It draws on `ground-patch-higher2`: above decoratives such as plants, below rails, belts, items, buildings and vehicles. Some decoratives (medium and big sand rocks) draw on `floor` or `object`, which no ground layer can beat, so `scripts/loading-zone.lua` removes decoratives overlapping the loading zone tile, as Factorio does under buildings. It does this whenever a depot is built by any means or turned, and for existing depots on first load. `tools/test_mod_setup.py` checks the layout with Lua 5.2.
- **Roads and deliveries.** `jatz-road` (`prototypes/roads.lua`) is a floor tile like stone path. `prototypes/off-road.lua`, run from `data-final-fixes.lua` so every mod's tiles are included, gives every other tile the `jatz_off_road` collision layer. Both road tiles (`jatz-road` and `jatz-depot-road`) carry the `jatz_road` layer, and the same file adds it to every buildable entity (an item's `place_result`, or with `placeable_by`) except belts, pipes, train tracks (with rail ramps and supports) and vehicles (cars, spidertrons, rolling stock), and except entities that collide with nothing. It goes in every mask the entity uses on the ground (`ground_masks`): `collision_mask` and, for gates, `opened_collision_mask`, since an open gate switches to it; add any other ground-level alternate mask a future type has. So nothing else, depots included, can be built or ghosted on road (and road can't be laid under it); a depot's loading zone tile is outside its box, so it can be road. The delivering freighter, `jatz-freighter-drone` (`prototypes/freighter-drone.lua`), is a hidden unit whose only collision layer is that one (tiles only), so the engine's pathfinder routes it over road and nothing else; there is no road-network bookkeeping in Lua. Its collision box is 0.4 tiles (±0.2): the engine's units overshoot a right-angle turn (about 0.3 tiles at the base speed, more when faster), and the 0.8-tile box it had pinned freighters against the off-road corner across a junction, where they slid sideways before driving back at an angle; with the smaller box they swerve and settle (the owner's choice, November 6, 2026). Keep its `path_resolution_modifier` at the default: at 1 the engine found no path for that 0.8-tile box on a one-tile road. `scripts/logistics.lua` registers provider and request depots, and sends freighters from each short request depot's loading zone to the provider holding the item that is nearest **by road** (both loading zones must be road; depots lay their own, see below). Road distance comes from `surface.request_path` with the freighter's own box and mask, asked one provider at a time in straight-line order; the search stops at the first candidate already farther in a straight line than the best road found, since a road is never shorter. A provider with no road route goes on cooldown and no freighter is sent towards it. Each search carries a token, and its owner (the request depot, or the trip of a freighter being rerouted) holds the token of its one current search. A road or depot change, a changed request, a busy pathfinder (`try_again_later`) or a 10 s timeout replaces or drops the token, so stale answers neither set cooldowns nor send freighters, and the search starts afresh: at the next dispatch for a depot, at once or on the next once-a-second check for a freighter. A freighter waiting for a reroute stays stopped (re-planning and command completions skip it), and if the provider found is emptied or removed meanwhile it searches again rather than leaving. `on_configuration_changed` restarts all searches. `tests/lua/logistics.lua` plays these races out against a fake runtime with Lua 5.2 (run by `tools/test_mod_setup.py`), with the freighter slot's sending, returning, losing and handing back; extend it with any change to the search or the freighters. **Buffer depots** (`jatz-buffer-depot`) are requesting depots like request depots (`logistics.requesting`; their own request, freighters, panel, copy and paste, refunds), but candidates for their freighters are providers only, so stock never bounces between buffers, and they send nothing anywhere. Request depots (item and liquid, never buffer depots) take buffer depots as sources too, and `from_buffers` (the panel's "Request from buffer depots" checkbox, like a requester chest's; carried by copy and paste and blueprint tags; `set_from_buffers`/`get_from_buffers` in the remote interface) decides which kind is ranked first (`first` in `candidates`). Set, buffers come first: the search asks about buffers before providers and never asks about a provider once a buffer has a road, so a nearer provider loses to any reachable buffer; providers cover only what no buffer can. Unset (the default), providers come first and buffers are the fallback, by the same rank rule: a buffer is asked about only when no provider holding the item unpromised and not on cooldown has a road route, so it covers only what no provider can (the owner's choice, November 4, 2026: before, an unset depot ignored buffers even with every provider empty). **Full loads only:** request and buffer depots, item and liquid, have `depot.full_loads` (the panel's "Full loads only" checkbox; carried by copy and paste, blueprint tags (`jatz_full_loads`) and so undo; `set_full_loads`/`get_full_loads` in the remote interface; off by default; the owner's request, November 7, 2026, so freighters don't drive out for a single ore). Set, `logistics.full_load(depot, trip)` is the least a freighter may set off to load, and what it carries: its capacity for the item, or the request if that is smaller, so small requests still come, whole. A new freighter's capacity is the force's (`cargo_stacks` times the stack size, or `fluid_capacity`); one already out carries its own cargo inventory's size, fixed when it set off (fluid: `fluid_capacity`, which `arrived_at_provider` reads as it loads). Every decision to send a freighter towards a depot applies all of it: `dispatch` waits (status `full-load`, yellow) while the depot's room is below it, `candidates` (given the threshold by `search_providers`) skips depots whose unpromised stock is below it, and `finish_search` checks both again. A reroute is such a decision too (Sourcery's and Copilot's review of ec3533b): `reroute` sends the freighter home empty when the depot's room besides its other freighters' (`need(depot, id)`) is below its full load, and a reroute that finds a provider plans a full load afresh (`min(room, unpromised, carries)`) rather than keeping what it set off for. `full_load` is on the module table to spare a local: Lua allows at most 200 active locals in a function, a file's main chunk included, and `scripts/logistics.lua` reached exactly 200 on November 7, 2026, so a new top-level `local` failed to load. Issue #69 splits it into modules along its seams (run-over code first, to `scripts/impact.lua`: 191 left); count before adding top-level locals there (its issue has a probe script). **Priority:** provider and buffer depots have a priority from 1 to 10 (`depot.priority`, 5 until set: `PRIORITY_DEFAULT`; `set_priority`/`get_priority` in the remote interface, which round and clamp; a slider in the panel: buffer depots have it at the top, above their request, provider depots get a panel with only the slider). It orders depots within their kind only: a candidate's `rank` is its kind (the kind asked about first 0, the other `PRIORITY_MAX`) plus `PRIORITY_MAX - priority`, so every depot of the first kind still comes before any of the other, a higher priority before a lower one however near, and nearest by road among equals; the search's rank rule (stop asking once a rank has a road) covers it unchanged. Changing a priority restarts the searches under way on its surface (`restart_searches`). Copy and Paste settings and clones copy it between provider and buffer depots; blueprints keep it as a `jatz_priority` tag when it isn't 5, applied (if a number) to provider and buffer depots built from the ghost. **Liquid depots** (`jatz-liquid-provider-depot`, `-request-`, `-buffer-`; storage tanks with one fluid storage, holding 25,000; the liquid provider's and liquid buffer's sizes are startup settings in `settings.lua`, `jatz-liquid-provider-depot-capacity` and `jatz-liquid-buffer-depot-capacity` (1,000 to 1,000,000, 25,000 by default), read by `prototypes/depots.lua` and named in the locale with the depot's item icon; deliveries read the size from the tank (`get_fluid_capacity(1)`), never a constant, and the check mod's `settings-updates.lua` runs with them at 40,000 and 15,000) take the same roles in `logistics.depots` and are marked `depot.fluid` (`logistics.liquid`): a liquid request depot requests a fluid (`set_request` checks `prototypes.fluid` for liquid depots and `prototypes.item` for item depots), has the same panel (fluid chooser filtered with `FluidPrototypeFilter`s only, which have no `is-parameter`: parameter fluids are left out by their `parameters` subgroup; anchored to `pipe_gui`, the window storage tanks open in 2.1, which removed `storage_tank_gui`; a new fluid request starting at 1000), freighters, from-buffers checkbox (with the same fallback to liquid buffers when unset) and priority, and candidates must be the same kind (`provider.fluid == depot.fluid`), so items and fluids never meet; copy and paste between kinds copies nothing. A fluid trip has `trip.fluid = { amount, temperature }` instead of a cargo inventory (`cargo_amount`/`cargo_empty`), carries at most `FLUID_CAPACITY` (500, Transport Drones' default drone fluid capacity), loads with `remove_fluid(1, amount)` (Factorio 2.1 removed `LuaEntity::fluidbox`: use `get_fluid(1)`, `get_fluid_capacity(1)`, `remove_fluid(1, n)`, which returns the fluid with its temperature, and `insert_fluid`), keeps the temperature, and unloads with `insert_fluid`; fluid that doesn't fit goes back to the provider (state `RETURNING`), and fluid that can't go anywhere is lost (it can't be spilled). A tank holding another fluid gets no room (`need` returns it) and the status `other-fluid` (yellow). Every request and buffer depot, item and liquid, gets a **truck chest** (`jatz-truck-chest`, `prototypes/truck-chest.lua`: an invisible, unselectable, indestructible twenty-slot container at the depot's centre that collides with nothing, inserters ignore (`no-automated-item-removal`/`-insertion`) and blueprints skip), made by `logistics.add` (and `add_all` for older saves, or `truck_chest()` on demand). Robots bring freighters into it, never into the depot: storage tanks have no item inventory, and inserters or loaders unloading an item depot's chest onto a belt took freighters robots had just put there before the next dispatch moved them into the slot, so the depot asked robots for more, over and over (the owner's video, November 7, 2026; the check mod's `deliveries.unloaded`, a request depot a burner inserter empties, reproduced it). `truck_chest(entity)`/`freighter_chest(entity)` map a requesting depot to it; every freighter request, removal and count goes through them, and the freighters then move into the slot as usual. Freighters put in an item depot's own chest, by hand or by an inserter, still move into the slot (`absorb_freighters` takes from both chests, and `logistics.waiting_freighters` counts both); ctrl+click and shift+click in its window go to its own chest, which `take_in_freighters` reads (a liquid depot's is its truck chest). Freighters asked of an item depot's own chest by an item request proxy targeting the depot (a blueprint ghost's insert plan, a request from a save from before, another mod's) are asked of its truck chest instead: `trim_freighter_requests` drops those plans, from every proxy targeting the depot (looked for by position: `item_request_proxy` names only the first found, which may be another item's), and requests them again, added up, as part of the target, which they become if it has none; `apply_tags` trims every requesting depot as it is built, so a ghost's plan moves before robots could bring any (robots taking freighters from an item depot's own chest, in a save from before, stop, and those stay). A liquid depot's blueprint keeps its freighters only as the `jatz_freighters` tag (a storage tank ghost can't carry an insert plan), and `apply_tags` asks robots for them with `match_freighters` when it is built. The truck chest goes with its depot (`on_object_destroyed`); mining a depot hands the freighters in it to the miner; a cloned truck chest is destroyed, the cloned depot making its own. Request depots hold their own freighters: up to 100 freighter items (`FREIGHTER_CAPACITY`; the item still stacks to 10) in a freighter slot, a script inventory of ten stacks per depot (older one-stack slots are resized) shown as one slot in the request panel; requests, removals and blueprint insert plans spread over chest stacks (the truck chest's, a blueprint's the depot's own) a stack at a time, and taking freighters into the cursor stops at one stack; freighters put in the depot's chest or its truck chest move into it on the next dispatch (those in its own chest stay, as cargo, when freighters are the request); freighters a player moves in by ctrl+ or shift+click in the depot's window, or ctrl+click on the depot in the world, move at once (`take_in_freighters`), and those that don't fit go back to the player's inventory. `on_player_main_inventory_changed` and `on_player_cursor_stack_changed` (registered in `control.lua`) work out what the player moved: how many fewer freighters they carry, inventory and cursor together, than before (counted when they open or point at a request depot, and at every change). Placing from the cursor counts, so a freighter dropped onto the ghost of a requested one moves to the slot at once and the chest slot shows the rest of the request again straight away; moving freighters between inventory and cursor counts as nothing. Freighter requests are lowered by editing the proxies' plans in place (`reduce_freighter_requests`), not by cancelling and requesting anew. Factorio's open container window doesn't redraw a chest's requested-item ghosts for script changes (seen in the owner's video: the ghost kept showing 5 for a request of 4 until the window was reopened). Reopening it by script (over two ticks; within one tick does nothing) worked but visibly flashed the window, and the owner chose no flash: the chest ghost updates when the window is next opened, and the panel's freighter line shows the live count instead (requests are now on the truck chest, so the depot's window shows no ghosts for them at all), a green "+N" while N freighters are requested, capped by how many more the chest holds than when last seen (`depot.chest_seen`), so freighters already in the chest stay. The depot is the open one, or the selected one for ctrl+click in the world. Only freighters, of any quality: other items moved in stay in the chest as in any container. Freighters waiting in the chest for robots to take away stay too, by count (`logistics.leaving`), so more merged into their stack still move. Construction robots can't reach a script inventory, so freighters are requested like modules: `request_freighters` adds a freighter insert plan (one empty chest stack, 0-based index) to an `item-request-proxy` targeting its truck chest, never more than the slot has room for counting freighters out, in the chest and already requested, and on top of freighters still waiting for a free chest stack (its target); robots fill the truck chest and the freighters then move to the slot. The panel does this when the cursor holds a freighter ghost (remote view, or none in hand); in remote view it never moves items by hand: a click with an empty cursor cancels the freighter requests (`cancel_freighter_requests`, which leaves other requests alone), and a right-click has robots take the slot's freighters away (`remove_freighters`: they move to an empty truck chest stack with a freighter removal plan, which the chest-to-slot move skips; right-click again: `cancel_freighter_removal`). Beside the slot (whose number is the freighters at home) a short line always shows how many are out on the road ("3 out", `request_gui.freighter_caption`), so home and out read at a glance, followed by a green "+N" while N freighters are requested; the full breakdown (robots bringing or taking freighters, the slot's limit) is the tooltip of the line and the slot. Pipette over the slot (`jatz-pipette`, a custom input linked to the game's pipette control, with hover tracking via `raise_hover_events`) calls `LuaPlayer.pipette` for the freighter, ghost allowed. A depot sends at most one freighter a second (`SEND_SPACING`, enforced per depot, not just by the dispatch cadence), so they leave one after another, while what the depot still needs, less what its freighters are bringing (`committed`: promised loads outbound, cargo inbound), is above zero and a freighter is in the slot. Each trip promises (`planned`) what it will load: the rest of the need, as far as the provider has it unpromised (`available`: its stock less the promises of the trips driving out to it, filed by provider and item in `storage.promised`; see **Spreading the work** below) and it can carry (ten stacks), so the next freighter goes to the next provider nearest by road and large requests are gathered from several. Trips only count towards (`committed`) and hold provider stock for (`available`) the item their depot currently requests: changing the request zeroes the outbound trips' promises, and a rerouted trip promises at most what its new provider has unpromised. The freighter item rides with its trip (`trip.truck`) and goes back into the slot whenever the trip ends; it is lost only if the freighter is destroyed (`lose`: from `on_object_destroyed`, or a command completed by a freighter that is gone). A freighter killed by enemies first fails its command at 0 health while still valid; `on_ai_command_completed` ignores that, so it isn't taken home as a failed route. One killed by a script (`LuaEntity::die`: the console, the editor, another mod) fails it with its health still showing (probed on 2.1.24), so every failed command waits for the next tick (`storage.failed_trips`, handled by `logistics.failed_commands` first in control.lua's `on_tick`): a freighter gone by then is lost, any other lost its way, but only if that command is still its latest. Every command a freighter gets goes through `logistics.command`, which counts them (`trip.command_id`), and a failure notes the count it failed at: a command given meanwhile (its request depot removed, a re-plan, a reroute) replaces the failed one, which is then over, so a loaded freighter sent back to its provider in that tick isn't taken for failed again and its cargo spilled (Pullfrog's review of 66d57e9, reproduced on 2.1.24). Taken home at once, it went back into the slot for free and its depot asked robots for no replacement. The delivering freighter is repairable, so construction robots repair it like any of the player's entities (the owner's report, November 6, 2026). A lost freighter's depot asks robots for a replacement: `match_freighters` to what it had before the loss (or its `freighter_target`, if higher), so the usual target rules (`trim_freighter_requests`) keep the request, and ask for it as soon as a chest stack is free if none is when it is lost, and a freighter put in by hand counts. **Enemies:** (`scripts/impact.lua`, called through `logistics.on_impact_tick`/`on_impact_share`, which deals the looks over the trips' phases) the delivering freighter is a military target (`is_military_target`, a unit's default), so enemies attack it. Every command it gets has `distraction = none`, so it never fights back or turns aside. Every 20 ticks (`IMPACT_INTERVAL`; control.lua's `on_tick` runs `on_impact_share`, which looks at the freighters of every twentieth tick of the second's phases (`trip_phases`), so each looks exactly every 20 ticks; every 10 ticks before, halved for the stress map's garbage, the owner's choice, November 6, 2026: a freighter at its base speed covers 4 tiles between looks, every one of them searched), each freighter that moved since the last look damages the enemy units (`unit`, `spider-unit`, `segmented-unit` of forces its force is at war with) in the ground it crossed, plus `IMPACT_REACH` (0.4 tiles) either side, the width its collision box had before it was narrowed, so hits don't follow the box. The ground is counted first (`count_entities_filtered`, one reused filter table) and listed only when something is in it. With no entity of those types in the game but freighters (`units_exist`: `LuaForce::get_entity_count` for each such prototype except the freighters', asked at the start of each round), no freighter looks, and the first look once there are some only notes where freighters are (`storage.impact_paused`). Each takes `IMPACT_DAMAGE` (200) impact damage, at most once a second per freighter (`trip.hits`), with the freighter as source and cause. Damage runs other mods' handlers there and then, so the freighter and each enemy are checked valid before anything is read from them. Characters, buildings and other freighters (in any paint, `paint.is_drone`) are never hit, and nothing collides. A destroyed freighter dies like the drivable one: `dying_explosion` and `corpse` are the base car's (the car's wreck, removed after 15 minutes). **Pollution:** each freighter out pollutes `POLLUTION_PER_SECOND` (0.005, Transport Drones' default), added at each freighter's once-a-second check with `surface.pollute` and credited to the freighter in the pollution statistics. A freighter with nothing to load, or whose reroute finds no provider, drives home empty to park. The slot holds 100 counting freighters out. Mining a request depot (player, robot or platform: `on_*_mined_entity`, registered in `control.lua` and checked through it by `tests/lua/control-events.lua`, routed to `on_depot_mined`) hands all its freighters, in the slot and out, to the miner's buffer; a depot that dies, or is removed by a script raising `script_raised_destroy`, leaves them on the ground where it stood, freighters still in its chests included (`on_depot_destroyed`, before the entity goes, for its own chest; `on_object_destroyed` for its truck chest); one removed silently leaves its slot, trip and truck chest freighters there from `on_object_destroyed`, which Factorio raises at the end of the tick or the next: a depot its once-a-second check (`check_depot`) or `add_all` finds gone first is handed to `on_object_destroyed` there and then, so every way a depot goes ends in the same cleanup. A freighter arriving to load or unload first stands at the loading zone for 1 s (`LOADING_TICKS`): `on_ai_command_completed` gives it a `stop` command with `ticks_to_wait` and marks the trip `loading`, and the loading or unloading happens when that stop completes. Re-planning skips a loading trip (it plans its route afresh once done), `drive` clears the mark, and a removed depot sends a freighter standing there on at once. One coming home empty parks without stopping. Once loaded, a freighter shows its cargo in alt mode as machines show their recipe (`show_cargo`): the item's or fluid's icon over `utility/entity_info_dark_background`, drawn with `rendering.draw_sprite` on the `entity-info-icon` layer, targeting the freighter so the sprites move with it and go when it leaves the map; `repaint` swaps the unit and so drops them, so they are drawn after it, both on loading and in the once-a-second check's deferred repaint; an empty freighter draws nothing. `tests/lua/logistics.lua` fakes `draw_sprite` strictly (2.1's parameters, entity info layers, existing sprites). At the provider a freighter loads what it promised, as far as the depot (counting its other freighters) still needs and has room for (`get_insertable_count`), only if the request is still for that item; it brings it back, unloads and parks. Cargo travels as real stacks in a script inventory (`transfer_stack`, `insert` of the stack), never as a name and count, so item data (equipment, spoilage, health) survives; keep it that way. Any failed route puts that provider on a 10-second cooldown for that request; a loaded freighter whose way back is lost returns the cargo to the provider, and only spills it (marked for deconstruction) if that fails too. Changes take effect at once rather than waiting on timers. When road is removed or covered (any tile event, including `script_raised_set_tiles`), every freighter on that surface re-plans, and a route that no longer exists fails in the same tick instead of after the engine's ~6 s stuck timeout. When road is laid, or a depot is built, turned or flipped, that surface's cooldowns are cleared. A removed provider stops its outbound freighter while a search from where it stands finds the next provider nearest by road; a removed request depot sends cargo back to the provider, and an empty freighter just leaves. Re-planning replaces a unit's command, so `behavior_result.deleted` completions are ignored. See **Fuel** below. Clones of depots are registered with their request; cloned freighters are removed. Copy and Paste settings copies the request and asks robots for the freighters the destination lacks to match the source's (slot, out and coming: `match_freighters`). Blueprints, including copy and paste, keep a request depot's request as a `jatz_request` tag and its freighters as an insert plan into the chest (`on_player_setup_blueprint` → `setup_blueprint`; the blueprint may be the event's record or stack, `blueprint_to_setup` or the cursor, any of them nil); setting a blueprint up again replaces those settings (dropping ones the depot no longer has), keeps other tags and other items' insert plans, and puts freighters only in chest stacks those plans don't use; freighter counts for copying and blueprints are `freighter_total` (slot, out, chest not leaving, coming). A depot built from the ghost takes its request from the tags (`apply_tags`, from every build event, using tags only if well formed) and gets its freighters through the ghost's item request proxy, whose freighter plan it moves to its truck chest at once (see the truck chest above). **Blueprint parametrisation** (`scripts/depot-settings.lua`; issue reported by the owner, November 7, 2026, the freighters later that day): the game parametrises only its own entity settings, never a mod's tags, and 2.1.24 has no API for blueprint parameters (no parameter access on `LuaItemCommon`/`LuaRecord`, no event with their values). So `setup_blueprint` also puts each request or buffer depot's request (item or fluid, amount) and freighters (as their tags hold them) in the blueprint as `jatz-depot-settings` (`prototypes/depot-settings.lua`), a hidden constant combinator at the depot's centre: slot 1 of its first logistic section holds the request, slot 2 the freighter item and how many (counted whatever item parametrising puts there), and the game can parametrise both; setting a blueprint up again replaces the one at a depot it plans. A slot's count is an int32 (`BlueprintLogisticFilter.count`; the game refuses others with "Count out of bounds") while requests have no limit, so a request above 2,147,483,647 leaves slot 1 empty and stays in its tag only (Pullfrog's review of 22214f3). It exists only in blueprints: the game refuses blueprint entities no item places, hence its hidden item. Probed on 2.1.24: a blueprint's ghosts are all placed before their build events, and a combinator ghost's control behavior reads its sections (`get_slot`), so its ghost's build event (`depot_settings.built`, from control.lua's build events, filtered by `ghost_name` too; filters of one event combine with `or`) writes the request and freighters (as parametrised) into the request depot ghost's `jatz_request` and `jatz_freighters` tags at the same position, or sets them on a request depot already there (pasting over one; `match_freighters`), and destroys itself. Only a depot of the settings' own force takes them, both ways (Copilot's review of 22214f3: the settings collide with nothing, so they can be pasted over another force's depot). Built at once (the editor, a script), the depot built takes them in `apply_tags` (`logistics.take_request_settings`), tags or not (a player building over a ghost passes none on), before its tags'. If the settings' build event comes first, they set the depot standing there, and its own build event would then apply its tags, which hold the blueprint from before parametrising, so they also note what they gave it (`storage.depot_settings_given`, by unit number, for that tick only), which `take` returns (Sourcery's review of 22214f3). Nothing stays in the world, so saves need no migration, and blueprints from before keep working from their tags. The game allows `require` only while loading, so depot-settings sets `logistics.plan_request_settings` and `logistics.take_request_settings` as hooks, like the road monitor's. **Undo** (`scripts/undo.lua`): Factorio records a removal on the player's undo stack from the entity alone, so undoing it would bring back a bare ghost. So a depot or road network monitor a player removes has its settings worked out as a blueprint keeps them (`logistics.settings_tags`, the same `plan_settings` as `setup_blueprint`; an empty snapshot when it has none to keep, which still replaces settings an earlier attempt saved and keeps removals at one spot in order) just before it goes, while its chest still holds its freighters (mining hands them over before `on_*_mined_entity`), and put on its `removed-entity` undo action as the `jatz_settings` tag (`LuaUndoRedoStack.set_undo_tag`). Probed on 2.1.24 with a player: marking for deconstruction (as cutting does) makes the undo action just after `on_marked_for_deconstruction`, and the action keeps its tags through the robots' removal, so `on_marked_for_deconstruction` only notes who marked it (`storage.undo_marked`, forgotten only on `on_cancelled_deconstruction` or when it is gone, `on_object_destroyed`: a mining attempt can fail and leave it standing and marked, a player's full inventory say) and `on_robot_pre_mined` (or `on_space_platform_pre_mined`: liquid depots and the monitor have no gravity condition, so they can stand on a platform, which takes a marked entity within the tick) tags that player's action at once, with the settings as they are then (again, newest, after an attempt that left it). Every action tagged here is also marked with whose removal it is (`jatz_removal_of`, the entity's unit number, never reused), and no other removal ever takes it. Places in the history aren't identities: items are pushed on top, and at the history's limit (100 items, probed on 2.1.24; not in the API docs) each new one drops the oldest. Reading an undo item builds every action in it, so control.lua's `on_tick` looks, in the tick of the marking (its action is made just after the event), for all of a player's marked entities in one pass over their undo items (a cut of many depots is one item, read once; one marked later in that tick, by a script, is looked for the next tick), marks each action as its entity's and remembers its index within its item, which never changes. A robot or platform removal finds its action by reading that one tag of each item (`get_undo_tag`; an out-of-range index raises, hence `pcall`), never the items, and reads the items itself only if it came before the look (a platform's, within the tick). Mining by hand makes its undo item only after `on_player_mined_entity`, so `on_pre_player_mined_item` holds the settings (`storage.undo_mining`, the latest attempt per player) until `on_player_mined_entity` says it was removed, and only then do they wait (`storage.undo_pending`, a list per player) for control.lua's next `on_tick` to tag (given up after 60 ticks, never tagged later). Every waiting removal is matched in each pass, the current tick's too: the mining's undo item is pushed just after `on_player_mined_entity` (probed), so its action is there by then, and holding back a newer one would let an older removal at its spot take its action (a depot mined at one tick and a replacement at its spot the next, before the tagging, swapped their settings): a failed attempt leaves nothing waiting that a later removal at the same spot could take. Waiting settings are matched to removal actions by surface, name and position, newest to newest, so several at one spot each get their own, and never to an action marked as another entity's removal: the marked entities are located first in the same pass, so a replacement at the same spot marked for deconstruction before the tagging keeps its own action, and an action taken earlier in the pass is marked at once. `on_undo_applied` puts the action's tags (or, undone before they were put on it, the settings still waiting, taken only if a ghost came back: a cancelled deconstruction brings none and leaves them for their own action) on the ghost the undo brings back, looking for a ghost only when there is something to put on it (not for anything else undone) (`ghost.tags`, keeping its other tags), and its build, by robots or by the player (both pass a ghost's tags on, probed on 2.1.24), applies them like a blueprint ghost's: a request depot's freighters through `jatz_freighters`, the target its dispatch asks robots for. A removal undone before robots took the entity cancels its deconstruction instead: no ghost, and it still has its settings. Redo isn't handled (the stack keeps tags on redo items too, `get_redo_tags`). In the map editor with instant building an undo revives the entity at once, with no ghost to give the settings to (the changelog's "in editor mode undoing deconstructions ... instantly revive"); that mode isn't handled either. The mod's own entities and tiles (truck chests, Fuel depot tanks, freighters, item request proxies, depot road) are made and removed without `player` or `undo_index`, so they never go on a player's undo queue. `tests/lua/control-events.lua` fakes the undo stack; the check mod's `scenarios/undo` (run by `tools/test_mod.py` with `--test-scenario`, which gives it a player; the check mod builds nothing else then) checks the tagging (a failed hand mining included, and with Space Age a liquid depot cut on a space platform) and the rebuilds from ghosts given those tags (by robots, by the player and, with Space Age, by the platform) against the real engine. Pressing undo itself can't be scripted (`--test-scenario` is no simulation, so `game.simulation` and its `control_press` are nil, and `LuaUndoRedoStack` has no call that applies an item: probed on 2.1.24), so `on_undo_applied` is the Lua checks' only, and the graphical client's. Freighter requests remember what they are for (`depot.freighter_target`: the total the depot should end up with, set to all that was asked for before free chest stacks are looked for, so a chest with too few free stacks (it also holds the depot's cargo) delays requests rather than losing them. `request_up_to` brings a depot up to an absolute target (`match_freighters`, and the retries in `trim_freighter_requests`); `request_freighters` asks for that many more than the depot has or is already waiting for, so a second request adds to a delayed one and a retry never counts it twice; and from the blueprint's `jatz_freighters` tag for a built ghost). Every dispatch, and every time freighters are put in by hand, keeps the requests to it (`trim_freighter_requests`): requests beyond it are cancelled, and a shortfall nothing covers is requested again, because Factorio drops an item request a player fills by hand even when they put in only part of it; the target is forgotten once the depot has it all, or when the player takes freighters out or has robots take them away (no topping up against them). Freighter requests without a target (Factorio's own from a blueprint ghost: a player building over a ghost passes no tags on) adopt the depot's current total (slot, out, chest, coming) as their target, at every dispatch and when the player opens the depot, before they can fill anything by hand; `match_freighters` to a smaller count cancels the excess requests but never takes freighters away, so freighters put in by hand count towards it and a request already met by hand disappears; robots never overfill the slot. `on_configuration_changed` clears requests and ends trips for items whose mod was removed. Saves from the first version of this code carry cargo as a number: `upgrade()` converts them on use, because the mod version did not change. The console command `/jatz-freighters` prints, for the request depot a player has open or points at, everything the freighter requests are worked out from (slot, out, chest, coming, leaving, target, each request proxy's plans; `logistics.describe_freighters`): use it to see what the game actually did when freighter requests misbehave in play. The request panel (`scripts/request-gui.lua`) is a relative GUI on the request depot's own window. Its status is a light, not text: the game's own status indicator sprites (`utility/status_working` green, `status_yellow`, `status_not_working` red, `status_inactive` grey, style `status_image`) beside the request, with the status text as its tooltip. Green: stocked or on its way; yellow: the item is available but something is in the way; red: no provider has the item (nor, for a request depot, any buffer depot: buffer depots fetch from providers only); grey: nothing requested. Every status in `logistics.status` needs an entry in `request_gui.lights` (`tests/lua/control-events.lua` checks). `control.lua` owns every event registration, since Factorio keeps one handler per event. The remote interface `jatz-distribution` (`set_request`, `get_request`, `get_status`, `set_circuit`, `get_circuit`, `add_freighters` (within the slot's limit; no raw inventory is exposed), `freighter_counts`, `request_freighters`, `requested_freighters`, `cancel_freighter_requests`, `remove_freighters`, `cancel_freighter_removal`) is what the check mod uses.
- **Spreading the work.** Every depot and every freighter out is checked once a second, but not all in the same tick, so hundreds of depots and thousands of freighters never stall the game (issue #37: the stress map's dispatch tick took over a second). control.lua's `on_tick` runs `logistics.on_tick_share`: each freighter is checked at its own tick of the second (`check_trip`: fuel burned and shown, pollution, a search that timed out, a tank run dry, a deferred repaint), given when it sets off (`schedule_trip`: the tick with the fewest, in `storage.trip_phases`, so every player's game agrees; `trip.id` follows a repainted trip). Its checks come exactly a second apart, the first within a second of setting off: fuel is burned by the straight-line distance between checks, and only because every stop (`LOADING_TICKS`, no shorter than a second) then has a check in it are the way out and the way back never measured as one leg, which would cancel out (Pullfrog's review of 46df83d: checks a second apart only on average let a one-tile round trip park with a full tank). So phases outlive configuration changes (`add_all` leaves `storage.trip_phases` alone; trips no longer out leave the lists when their tick comes), and the first schedule of a save from before phases burns each trip's fuel as it deals the phases out (Pullfrog's review of 0125590), and depots go by `check_phase` (`check_depot`: dispatch, the Fuel depot's tank, the circuit status). Requesting depots fetching the same item or fluid on the same surface are checked in the same tick, as every depot was before, each such group in its own tick (`storage.check_phases`, the next group 37 ticks on); other depots by their place. Checked one by one instead, later depots found the near providers' stock promised to earlier ones and drove past them to farther ones: 14% fewer deliveries in the UPS emulator with the same freighters. Depots checked in the same tick share one look at the depots that can supply them (`suppliers`, cached only while a tick's depots are checked, since that changes no stock or promise). That look, and the search for Fuel depots (`fuel_candidates`), go through `storage.depot_index[surface index][role]` (`depots_at`), so they read only the depots of that role on that surface, not every depot. `logistics.add` and the two removals (`check_depot` finding the entity gone, `on_object_destroyed`) keep it up to date, and it is built afresh when missing (`add_all` drops it). It isn't keyed by force: a script can change an entity's force without an event, and merging forces moves entities, so the force is checked as each depot is read. A provider's unpromised stock is its stock less the promises filed for it (`storage.promised[provider][item][trip.key]`), which `promise` files again whenever a trip's provider, state or promise changes, and `file_promises` files afresh for a save from before and after `add_all`. What a request depot's freighters are bringing (`committed`, read by `need`) is filed the same way, by the same calls: `storage.coming[request][item][trip.key]` holds each trip's `bringing` (its promise on the way out, its cargo on the way home), filed by `file_coming` from `promise`. So call `promise(trip)` after every change to a trip's state, promise or cargo, including state changes alone (`arrived_at_provider`, a route lost on the way home, fluid that didn't fit, a depot removed). Cargo that spoils is the one change without a call: the game turns a whole stack into its spoil result just after its `spoil_tick` (on that tick it is still there), inside the cargo inventory and with no event. So `file_coming` also files the earliest `spoil_tick` of a returning trip's cargo (`storage.spoiling[request][item]`, only for items whose `get_spoil_ticks()` is above 0), and `committed` files that depot's trips for the item again (`file_spoiled`) once the tick has come. `tests/lua/logistics.lua` checks `storage.coming` against every trip at each of its checks, and that every spoiling stack's tick is filed (`coming_filed`). Freighters in a chest are counted in one call (`get_item_count_filtered` with a name and no quality: every quality), and a chest's item request proxies are searched for only when `item_request_proxy` says it has one. `logistics.on_tick` runs every check at once: `tests/lua/logistics.lua` drives the deliveries with it, and checks the spreading itself (`on_tick_share`, `on_impact_share`). Keep work done every tick from making garbage where it can: Lua's garbage collection is most of what still stutters on the stress map. The collector's work per tick grows with what the mod allocates per tick, and a collection that frees much of the heap at once takes several milliseconds in one tick. Measured on 2.1.24: reading a position makes 200 bytes, a setting (`settings.global[...]`) 200, an inventory 144, a tile 144, a prototype 112, and a method read off an object (`surface.pollute`) 88; `valid`, `name`, indices and a bound method called again make none. So the fuel settings are read once a tick and handed to every freighter's check (`check_trip`), each surface's `count_entities_filtered` and `pollute` are bound once a tick, a provider keeps its inventory (`depot.stock_inventory`) and its bound `get_item_count` (`stock_counters`, Lua only, rebuilt after a load), item stack sizes, the freighter's speed, which items and fluids exist and what fuels give are read from prototypes once a session (they don't change while the game runs), a force's research levels are kept (`research_of`: `storage.research_levels[force index]`, forgotten on any research finished or reversed, forces reset, made or merged, configuration changes, and after a minute), impact looks reuse the position that tick's check read (`trip.at_tick`), freighter fuel statuses reuse their tables (`FUEL_STATUS`, `trip.fuel_shown`), `loading_zone.tile_centre` reads a position once, a depot keeps its loading zone tile and whether it is road (`loading_tile`: `depot.zone`, read again when the depot turns, its surface's road changes, or after five minutes), and `load` skips the leading cargo stacks that can take nothing more (full, or holding another item). It never skips a stack of the item with room that refused one stack: stacks merge only when their quality and data (health, tags, durability) match, so a later stack can still top it up (Pullfrog's review of `187a87e`: skipping it left damaged machines behind). `tests/lua/logistics.lua`'s item stacks hold at most their stack size and merge only with matching `health`, as in the game. Fewer, larger collections cost more than many small ones too: the collector's last steps of a cycle (clearing what is finalized, sweeping strings) take milliseconds in one tick, longer the more engine objects (positions, inventories, entities, prototypes: each is finalized) were made. Tuning the collector (`collectgarbage("setpause"/"setstepmul")`, explicit steps) was tried and made the worst tick worse. The engine's path answers were the largest share: every `on_script_path_request_finished` builds the whole route in the mod's Lua state, a table per tile, about 57 KB an answer on the stress map. So depots remember road lengths (`storage.road_lengths[surface index]`: `lengths` by `road_key`, from loading zone to loading zone, false for no road, and the `ticks` they were found), asked again after `ROAD_MEMORY_TICKS` (five minutes), forgotten for a surface whenever its road changes (`on_roads_changed`, which also counts up `storage.road_versions[surface index]`: an answer to a question asked before the change isn't remembered) and on configuration changes; freighters' reroutes, which start wherever the freighter stands, always ask. A remembered length is answered as the pathfinder's would be (`answer_remembered`, from `on_tick_share` and `on_tick`, through `storage.road_answers`): never during the tick's depot checks (`checking_depots`), so a group still decides together, and paced by search, not by answer, since each search that ends sends a freighter off: a search given its remembered answer takes its next remembered ones at once (`give_remembered`), until it ends or asks the pathfinder, and searches are given their answers in the order asked, at least `REMEMBERED_PER_TICK` (3) a tick, or as many as clear the queue evenly within `DISPATCH_INTERVAL` of the oldest's question. A search made stale meanwhile is dropped from the queue without taking a turn. Pacing answer by answer, with each search's next answer queued behind every other search's, let a large group's searches each wait their turn for every candidate, so none finished within `SEARCH_TIMEOUT` and every one restarted; `tests/lua/logistics.lua` sends 300 depots comparing 7 providers each from remembered roads (Pullfrog's review of `5832360`). Answered at once instead, depots sent a third more freighters and the worst tick grew. Depots still send freighters off sooner than with the pathfinder alone (the owner's choice, November 6, 2026, to keep it): in the UPS emulator, which answers the pathfinder's questions a few ticks late, 31% more items are delivered on the standard preset.
- **Fuel.** Freighters carry fuel as energy (`trip.energy`, joules), burned at each freighter's once-a-second check (`check_trip`) by the straight-line distance driven since the last sample (`burn`, `trip.at`), at `jatz-freighter-fuel-per-tile` kJ a tile, from a tank of `jatz-freighter-fuel-capacity` MJ (runtime-global settings, `settings.lua`; 10 kJ and 20 MJ by default, so a full tank lasts 2,000 tiles, Transport Drones' default per drone; 0 per tile turns fuel off). Fuel comes from game data, never a list: any item with `fuel_value > 0` (any fuel category, any mod) and any fluid with `fuel_value > 0` (the base game has none, so `data-final-fixes.lua` gives petroleum gas 400 kJ a unit, a full tank being 50 as Transport Drones' fuel per drone, unless another mod has given it a fuel value). Items go in whole (`refuel` rounds up), so an item worth more than a tank (some mods' items hold 10 GJ) fills a freighter past its capacity, and it keeps that. Parked freighters keep their fuel: `depot.fuel` lists the energies of the slot's freighters whose tank isn't exactly full (less, or more), lowest first; freighters without an entry are full (new ones come with a full tank), freighters taken out of the slot take the full ones first, then the fullest entries (`parked_fuel` trims to the slot count, at once in `take_freighters` and `remove_freighters`, so freighters put in afterwards come full), and `start_trip` sends the freighter with the most (chosen after its unit is created). A delivering freighter shows its fuel on hover as its status (`show_fuel`: `LuaEntity::custom_status`, a dot and `jatz-gui.freighter-fuel` with `logistics.energy_caption`, MJ or GJ; green, yellow below `LOW_FUEL` of a tank, red dry; nil while fuel is off), set when it sets off, at its once-a-second check, after filling up and after `repaint`, and written only when what it shows changes (`trip.fuel_shown`). The request depot's panel shows its slot's fuel under the freighter slot (`freighter_fuel` label: full count and lowest, every freighter's fuel in the tooltip; hidden while fuel is off). Unlike Transport Drones, nothing delivers fuel to request depots: freighters fill up themselves. Before each leg (`set_off`: setting off from home, leaving the provider, heading for a new provider after a reroute) a freighter checks its tank against the leg's road length (`trip.leg`, the search's `best_length`; the way home is never taken as shorter than the straight line) times `FUEL_MARGIN` plus `FUEL_RESERVE` of a full tank, capped at a full tank (`short_of_fuel`); short, it stands while a search finds the Fuel depot nearest by road (`seek_fuel`, the same token-owned `request_path` search as providers, `search.fuel`, candidates from `fuel_candidates`: same surface and force, road at the loading zone, holding fuel (`has_fuel`: a burnable fluid, or a burnable item, one with a `burnt_result` only while the chest has room for it), not on the request depot's cooldown), drives there (`trip.refuel`; `target` returns it), stands `LOADING_TICKS`, fills up (`refuel`: burnable fluid first, then items a whole item at a time, the last may overfill like a burner's current item; an item with a `burnt_result` leaves it in the depot and is taken only as far as there is room for it) and drives on to its target (`trip.refueled`: once a leg). The Fuel depot found emptied or removed during the search: it looks again among the rest. No Fuel depot (none with fuel, none reachable): it goes on (`go_without_fuel`, to `target`, which falls back to the provider's zone set at `start_trip` if the provider is already invalid), except a freighter still at home (`trip.departing`) that can't reach the provider on what it has, which goes back into the slot (never sent to wait at an empty Fuel depot) while its depot waits `RETRY_TICKS` (`retry_status`): `no-fuel` (yellow) when its road reaches Fuel depots but none with fuel, `no-fuel-depot` (red) when its road reaches no Fuel depot. A freighter at home searches empty Fuel depots too, ranked after those with fuel (`fuel_candidates(..., empty)`, rank 1), so the search tells the two apart. `dispatch` ends either wait early once `fuel_candidates` finds a Fuel depot with fuel, and building a depot or laying road ends it too (`retry_now`). Freighters only ever take fuel from Fuel depots: fuel in other depots is cargo. A tank that runs dry slows the unit to `DRY_SPEED` (`LuaEntity::speed`, writable for units in 2.1) and looks for a Fuel depot, or crawls on to its target, so a freighter is never stranded. A road failure to a Fuel depot puts it on cooldown and looks again; a removed Fuel depot sends its freighters to look again; a reroute drops a pending fuel detour (`set_off` decides afresh); timeouts and restarts repeat whichever search a trip had (`search_again`). **The Fuel depot** (`jatz-fuel-depot`, role `fuel` in `logistics.depots`, in no deliveries) is a 48-slot container, so fuel items go in by hand, inserter or robot, with a hidden storage tank under it for liquid fuel (`jatz-fuel-depot-tank`, `prototypes/depots.lua`: its pipe port and connector pictures, nothing else drawn, not selectable, collides with nothing, not blueprintable), since no entity type has both an item inventory and a fluid box of its own. `fuel_tank(entity)` makes it (`logistics.add`, `add_all`, on demand), and keeps its `direction` and `mirroring` the depot's on every build, turn and flip (`on_depot_changed`) and once a second (scripts turn entities without events); it goes with its depot (`on_object_destroyed`, or the depot's once-a-second check if that drops the depot first). Cloning keeps the liquid: a tank cloned with its depot is adopted by the cloned depot (`fuel_tank` takes an unowned tank at the depot's position, `stray_tank`, before making one; `on_cloned` keeps a cloned tank whose depot owns it or stands on it unregistered yet, `cloned_tank_kept`, whichever event comes first), a depot cloned alone gets the original tank's fluid (`set_fluid`), and a tank cloned without its depot is destroyed. Its fluid shows in the depot's panel (`fuel_contents`), with a flush button (`flush_fuel`, `clear_fluid_inside`, which empties connected pipes too, as a vanilla flush does). The remote interface has `freighter_fuel` (slot, fullest first, and out, in joules, with the capacity), `set_freighter_fuel` (every freighter in a slot) and `fuel_contents`. `tests/lua/logistics.lua` covers burning, the detour and its order, liquid before items, burnt results, staying home, going without, cooldowns, running dry, a removed Fuel depot and fuel turned off; the check mod covers a coal detour before loading (the freighter's hover status yellow on the way), petroleum gas at the mod's own 0.4 MJ, and a dry freighter that waits for fuel, then crawls to it.
- **Depot road.** Every depot lays `jatz-depot-road` under its loading zone sign when built (`scripts/depot-road.lua`), so road a tile away connects. It is a separate hidden tile (`prototypes/roads.lua`): it looks and drives like road (no off-road layer, `transition_merges_with_tile = "jatz-road"`) but has no item, and mining it gives nothing, so it can't be farmed. Being its own tile is what marks road the depot owns: `storage.depot_roads[unit_number]` records the tile position and exactly what it covered (tile, hidden and double-hidden tile), and when the depot is removed by any means (`on_object_destroyed`) or turned, that ground comes back, but only if the depot's road is still there and no other depot loads from the same tile. Nothing is laid over existing road, on water or on space platforms. A tile a player places over it, or mining it by hand, gives the spot to the player (mining puts back the covered ground, since mining alone would only reveal the hidden tile); the record becomes `false` so it isn't laid again on load. Depot road with no owner (a cloned area) is adopted, with its hidden tile as the ground. Existing depots get theirs on `on_init`/`on_configuration_changed`. `tests/lua/depot-road.lua` covers turning, mining and covering by hand, sharing (records copied exactly, a missing hidden tile included) and upgrades; `tests/lua/control-events.lua` loads the real `control.lua` and fires the game's events (build, turn, flip, removal, tiles placed, mined or set by players, robots and scripts) at its handlers, so a broken route fails; the check mod covers building, removal and connection. Tiles another mod's script sets over a depot's road (`script_raised_set_tiles`) give the spot up too.
- **Mining Drones.** With Mining_Drones, Mining_Drones_Remastered or Mining_Drones_Mod (optional dependencies in `info.json`; all three name their depot `mining-depot`, a 5 × 8 `assembling-machine`), the mining depot is an item provider depot (the owner's request, November 5, 2026, as Transport Drones does): `scripts/loading-zone.lua` adds it to `loading_zone.depots` only when `prototypes.entity["mining-depot"]` exists, since event filters and entity searches refuse unknown names, and gives it its own loading zone, 4.5 tiles from its centre behind the end opposite its mining area (Transport Drones' node position); from there it lays depot road, clears decoratives, follows turns and registers like any depot. `logistics.depots` gives it the provider role, and its stock is its output inventory (`inventory()` returns `get_output_inventory()` for it), where the drones put what they mine. Its priority panel anchors to `assembling_machine_gui`. `tests/lua/logistics.lua` checks it with and without the mod, `tests/lua/control-events.lua` loads `control.lua` as with the mod installed; `tools/test_mod.py --mod <zip>` runs the check mod's mining depot delivery (skipped without the mod) against the real mod, which CI can't download.
- **Circuit network.** Every depot has a four-direction `circuit_connector` (`prototypes/depots.lua`: liquid depots at the assembling machine's 3x3 spot; item depots and the Fuel depot, whose loading opening that spot overlaps when they face south (the owner, November 5, 2026), on their right-hand pillar below the painted band, `by_pixel(37, 28)`, which all four of their views have in the same place; containers with `direction_count = 4` need one per direction, so the steel chest's single one can't be used) and the base wire reach. Wires attached before this too (the reach was inherited), only without a connector sprite. Delivery depots have an enable/disable circuit condition modelled on 2.1's `LuaLogisticContainerControlBehavior.circuit_condition_enabled`/`circuit_condition` (`scripts/depot-circuit.lua`: `condition` normalises a CircuitCondition, dropping unknown signals, `signal-each` and special second signals; `allows` reads it; no first signal never holds, everything/anything as in the game). It reads one of two things, `depot.circuit_mode` (the owner's request, November 5, 2026: a depot's own stock must not count when it reads another depot's): **"network"** (stored as nil, the default) reads red and green through `get_circuit_network(wire_connector_id)` and `LuaCircuitNetwork.get_signal`/`signals`, less the depot's own contents on each wire, with no effect without a wire; **"contents"** reads only what the depot holds (`own_signals` in `scripts/logistics.lua`: items by quality, fluids floored, as a tank sends them) and needs no wire. Logistic chests, inserters and assembling machines read their own output back (they have a read toggle instead), and 2.1 has no API for one entity's share of a network, so "network" subtracts it: what the depot sends itself (`sent`: a `container` control behavior's `read_contents`, a `single_fluid_box`'s `send_contents` or `send_segment_contents` (its segment's fluid), on the colours `output_networks` allows; other kinds, such as a mining depot, aren't worked out) and what road network monitors on that network counted for it (`road_monitor.counted`, through the `logistics.monitor_counts` hook). Probed on 2.1.24: a depot's behavior exists once wired, reading or sending its contents; tank fluid goes out floored; and a wire carries what each entity sent at the previous tick's circuit update, so a transfer earlier in the tick isn't on it yet (700 wood taken out of 1000 still read 1000; Pullfrog's review of 08bed57). So what a depot takes back out is its contents (and a tank's segment fluid) sampled at the start of each tick: control.lua's `on_tick` (raised before `on_nth_tick` and the entity updates) runs `logistics.sample_circuits` over `storage.circuit_watch` (depots reading the network, kept by `set_circuit` and on load) into `depot.circuit_sample`, used all that tick (live contents only when not sampled this tick). Changes applied before any mod's `on_tick` (a player's own transfers) or by mods earlier in the tick are already in the sample for that one tick. - **Depots:** keep the fixed camera, ground pivot, `PROJECTION | tile grid compensation` parent, `SOCKET` markers and pipe shape-key drivers. Pipes must visibly reach the tank. After changes, run the geometry and junction inspectors, the renderer and packager, and the depot test fixture.

- When changing the default palette, update every place it appears (listed in each asset README).

## Testing rules

- **UPS.** Players may run hundreds of depots and thousands of freighters on several surfaces for hundreds of hours, so performance is a requirement. A pull request that can change what the game does each tick includes the before and after table from `python3 tools/benchmark_ups.py --factorio <factorio> --compare origin/main` (the template's "UPS before and after" section). That covers `control.lua`, `scripts/`, `data-final-fixes.lua`, prototypes the game simulates (entities, units, tiles, collision layers), what runtime settings do, and the benchmark or emulator. Recipe, technology cost, locale, icon, artwork, documentation and tooling changes don't run it; write "Not applicable" and why (the owner, November 6, 2026). `docs/benchmark.md` has the full list. The benchmark mod `tests/factorio/ups-benchmark_0.1.0` builds the map from `layout.lua` and `presets.lua` (pure Lua, also read by `tests/lua/ups-emulator.lua`); changing a preset, the layout or the nauvis seed (`NAUVIS_SEED` in `tools/benchmark_ups.py`, a seed with biters, so the impact checks' cost is always measured) invalidates the baseline in `docs/benchmark.md`, so re-record it in the same pull request. `tools/emulate_ups.py` runs the real `control.lua` against a fake runtime on the same map and counts exactly the Lua instructions the mod's own code runs per tick (and, separately, its calls into the runtime's functions); CI's **UPS benchmark** check compares a pull request with its base this way and only warns on a rise. Keep the emulator's fakes in step with the runtime API the delivery code uses, and wrap every new fake function in `native` (computed properties in `properties`), so the fake's own work is never counted; `tools/test_emulate_ups.py` checks that.
- Factorio test runners (`tools/test_factorio.py`, `tools/test_depot_art.py`) build their workspaces under `.local/`. Never touch the user's normal Factorio mods, settings or saves. Unit tests that need scratch files use Python's `tempfile`, which cleans up after itself.
- Headless runs, HTML previews and contact sheets don't prove visual quality. Visual changes need a graphical-client check.
- Keep machine paths, Factorio binaries, logs, saves and Python environments out of commits.
- Screenshots go in the pull request, not the repository. Only images used by the README belong in `docs/images/`, and only the Mod Portal page's in `portal/gallery/` and `portal/images/`.

## Continuous integration

CI (`.github/workflows/ci.yml`) is based on yuoki-quinityn's, but routed by repository **area** so a change only runs the checks for what it touched. `tools/ci_changes.py` reads the complete diff and decides; `CI result` is the one stable check to require.

| Area | Paths | Checks (`.github/workflows/area.yml`) |
| --- | --- | --- |
| Freighter | `assets/quinityn-freighter/`, the freighter test mod, `tools/test_factorio.py`, `tools/prepare_test_mod.py` | Lua and Python lint; Blender sources check when models, images or records change |
| Depots | `assets/depots/` (with the 1×1 archive), the depot test mod, `tools/test_depot_art.py`, `tools/test_depot_lua.py` | Lua and Python lint; generated-Lua test; Blender sources check when models, images or records change |
| Mod | The mod source at the repository root, `tools/package_mod.py`, `tools/test_mod.py` and its check mod, the UPS benchmark (`tools/benchmark_ups.py`, `tools/emulate_ups.py`, `tools/test_emulate_ups.py`, the benchmark mod, `tests/lua/ups-emulator.lua`), plus anything else that isn't documentation | Lua and Python lint; mod setup tests; for pull requests, the **UPS benchmark** check (`ups` in `ci.yml`): `tools/test_emulate_ups.py`, then the engine-free script cost against the base, in its summary and a pull request comment |
| Repository | `.github/`, the other `tools/` | Python lint, the `tools/test_*.py` repository tests, actionlint |

- Documentation (`README.md`, `AGENTS.md`, `CONTRIBUTING.md`, `SECURITY.md`, `docs/`, `concepts/`, licence files) runs no area checks.
- Shared lint configuration (`.luacheckrc`, `.stylua.toml`, `.ruff.toml`, `.gitattributes`) re-checks every area in full. Editing `ci.yml`, `area.yml` or the router runs everything.
- **Lua:** Lua 5.2 syntax, Luacheck and StyLua. Pull requests check the area's changed `.lua` files; pushes to `main` check all of them.
- **Python:** syntax and Ruff (syntax errors and Pyflakes). The frozen 1×1 archive tools are exempt from Pyflakes.
- **Blender sources** (`tools/check_blender_sources.py`, no Blender needed): every `.blend` is saved uncompressed by Blender 4.3; each model matches the hashes in its render, packaging and inspection records; freighter sprites match `checksums.json`; the freighter and every depot have an icon in Factorio's 120 × 64 mipmap layout (decoded and checked for blank levels and stray pixels), made from the current sprite sheets; the loading zone marking is a 64 px tile, not blank, and current with its drawing script; and the 1×1 archive matches its manifest. The art jobs then install the pinned numpy, Pillow and OpenEXR, exercise the real EXR sprite extractor with a small fixture (`tools/test_art_dependencies.py`), redraw the icons (`tools/make_icons.py --check`) and the marking (`make_loading_zone.py --check`), and require the committed pixels to match exactly. Re-render, re-package and re-inspect after editing a model, so the records follow it.
- Changes to `requirements.txt` run both artwork checks so dependency updates must reproduce the committed icons and marking.
- The routing job runs `git diff --check` on every change, except binary files.

**Downloads stay small for area checks.** Area jobs check out text only: blobs over 256 KiB and the binary types in `.gitattributes` are never downloaded, and an area's art is fetched only for its Blender sources check. So text files must stay under 256 KiB; mark larger generated files as `binary` in `.gitattributes` (the routing job fails with that advice otherwise). Keep the checkout exclusions in `ci.yml` and `area.yml` equal to the binary patterns in `.gitattributes`; `tools/test_ci_changes.py` checks that they match.

The installable-package job uses a full checkout when mod, repository tooling or artwork changes, builds the ZIP and verifies its contents, version records and checksum. It is included in `CI result`. Release automation and its tests are documented in `docs/releases.md`.

**A green `CI result` only vouches for the PR's own workflow.** `pull_request` runs use the workflows from the PR, so a PR that edits `.github/workflows/`, `tools/ci_changes.py` or the tools they call can change what is checked, or skip it. Review those changes line by line before merging, whatever CI says; only the owner merges.

Before pushing, format Lua with `stylua --config-path .stylua.toml <files>`, and run `luacheck`, `ruff check --config .ruff.toml` and the relevant `tools/test_*.py`. The tool versions are pinned in the workflow files. When an area or check is added or renamed, update `tools/ci_changes.py`, `tools/test_ci_changes.py` and the jobs in `ci.yml` together. The depot packagers generate `depot-definitions.lua` and `depot-pipe-pictures.lua` through `assets/depots/tools/depot_lua.py`, already in StyLua format; `tools/test_depot_lua.py` requires the committed files to match.
